## Executive Summary

A comprehensive diagnostic audit of the Grocery Demand Forecasting project was performed across all source scripts, datasets, serialized LightGBM models, and web application components. 

The pipeline demonstrates solid foundational concepts: separate modeling for perishables and non-perishables, LightGBM count-based regression, festival uplift modeling, and inventory cover calculations. However, **the audit revealed critical architectural disconnections, algorithmic errors, temporal data leakage, training anomalies, and unhandled runtime exceptions** that significantly impair model validity, production readiness, and reported forecast performance.

### Key Headline Findings:
1. **Model Training & Fine-Tuning Status:** The LightGBM models are **NOT fine-tuned** and are **only partially/improperly trained**. Hyperparameters are static heuristic defaults; there is no early stopping, no validation set during fitting, no time-series cross-validation, and an objective mismatch (Poisson deviance loss vs. MAE/MAPE evaluation).
2. **Two Disconnected Systems:** The trained LightGBM models are **never used** on the 48,000+ BigBasket products or the regional dashboard tabs. The regional dashboard displays numbers generated by pure random number generators (`np.random.uniform`), while the ML models only predict 32 synthetic SKUs.
3. **Severe Data Leakage & Evaluation Distortion:** Rolling features (`roll_mean_7`) calculate statistics using ground-truth sales from day $t-1$ across the holdout test set. This "teacher forcing" artificially inflates reported accuracy (reported ~10% MAPE). Furthermore, the holdout test set completely misses all major Indian retail festivals.
4. **Censored Demand Bias:** The forecasting engine trains directly on `units_sold` without unconstraining demand for stockouts, setting up a classic supply-chain "death spiral."
5. **Platform Incompatibility & Runtime Crashes:** Hardcoded Windows paths (`C:\Users\MR\Downloads\archive.zip`) cause `import_archive_products.py` and `build_bigbasket_regional_risk.py` to crash immediately with unhandled `FileNotFoundError`.
6. **Dead Code in Storefront:** A conditional short-circuit in `dashboard.py` prevents the 48,000 BigBasket catalog products from loading, reverting the customer store to only 32 synthetic items.
7. **Repository Bloat & Phantom Features:** A 370 MB Windows Oracle JDK (`oracleJdk-27/`) is committed in the root directory. Features advertised in `README.md` (OpenAI inventory copilot, SMTP emailing, `replenishment.py`) do not exist in the codebase.

## Detailed Audit: Is the Model Properly Trained and Fine-Tuned?

### 1. Model Training Status: **Partially Trained with Structural Flaws**
- **Convergence & Tree Count:** Both models fit 400 trees with `learning_rate=0.05` and `num_leaves=31`.
  - While training runs without crash, **no early stopping** (`callbacks=[early_stopping(...)]`) is configured.
  - No validation set is supplied to `model.fit()`. The model trains blindly for 400 iterations.
  - Evaluation curves show test MAE flattens significantly after ~250 iterations (Perishable test MAE at iter 200: 3.56, iter 400: 3.51). Additional trees yield diminishing returns while increasing latency and risk of overfitting.
- **Objective Function Mismatch:**
  - Both models are trained with `objective="poisson"`.
  - Poisson loss minimizes deviance: $2 \sum (y \log(y/\hat{y}) - y + \hat{y})$. This assumes the variance equals the mean ($\text{Var}(Y) = \mu$). In retail grocery demand, sales exhibit massive **over-dispersion** ($\text{Var}(Y) \gg \mu$), zero inflation, and heavy tails.
  - The model performance is evaluated and reported in terms of **MAE** and **MAPE**. Optimizing Poisson deviance does not mathematically minimize MAE (which corresponds to median regression / $L_1$ loss). If business operations care about MAE, training with `objective="regression_l1"`, `objective="huber"`, or `objective="tweedie"` is substantially more aligned.
- **Collinear & Redundant Features:**
  - Feature inspection reveals that `city_code` and `store_id_code` are **100% identical** across all 230,144 rows.
  - In `generate_synthetic_data.py`, `store_id` is derived directly as `f"{city[:3].upper()}-01"`. Passing both `city_code` and `store_id_code` to tree splits introduces redundant splits and dilutes feature importance without adding information.
- **Categorical Feature Portability:**
  - Categorical codes are generated via `df[col].astype("category").cat.codes`.
  - The integer mapping is **never serialized**. Neither a mapping dictionary nor an `OrdinalEncoder` is saved in `models/`.
  - If a production API or new dataset evaluates `models/lgbm_perishable.txt`, it has no reference to know which integer corresponds to "Mumbai", "Dairy", or "SKU0001".

### 2. Model Fine-Tuning Status: **NOT Fine-Tuned**
- **Zero Hyperparameter Optimization:**
  - There is no evidence of hyperparameter search (no Optuna, GridSearch, RandomSearch, or Bayesian optimization).
  - Hyperparameters (`max_depth=6`, `num_leaves=31`, `n_estimators=400`, `learning_rate=0.05`, `subsample=0.8`, `colsample_bytree=0.8`) are generic, hardcoded values.
  - Crucial regularizers (`reg_alpha`, `reg_lambda`, `min_child_samples`, `min_split_gain`, `path_smooth`) remain at default values.
- **Identical Configuration Across Heterogeneous Segments:**
  - Perishables (milk, vegetables, fruits, sweets) have short shelf-lives, rapid spoilage, high volatility, and extreme festival sensitivity.
  - Non-perishables (packaged snacks, beverages, household cleaners) have long shelf-lives, steady baselines, and lower festival peaks.
  - Despite these opposing dynamics, both models use the **exact same architecture, tree depth, and hyperparameters**.

### 3. Validation & Evaluation Integrity: **Severely Compromised**
- **Festival Void in Training (2021–2022):**
  - `festival_calendar.py` only defines festival dates from 2023 through 2027.
  - However, `generate_synthetic_data.py` generates data from **2021-08-26 to 2026-08-25**.
  - For the first 16 months (August 2021 to December 2022; **59,520 rows or ~26% of all training data**), `festival_uplift()` returned 0 uplift.
  - In `features.csv`, for all of 2021–2022, `nearest_festival` is stuck at "New Year 2023" with `days_to_festival` reaching up to 465 days, and `is_festival_week = 0`.
  - This injects a massive artificial distribution shift: 26% of the data has completely flat festival behavior, while 2023–2026 has strong spikes.
- **Evaluation Holdout Bias (Missing Major Festivals):**
  - The holdout period is the last 90 days of the dataset: **May 27, 2026 to August 25, 2026**.
  - During this entire 90-day window, there is **only ONE minor festival**: Independence Day (weight 0.3).
  - **Zero major retail festivals** (Diwali, Holi, Dussehra, Ganesh Chaturthi, Eid, Navratri, Makar Sankranti) exist in the holdout evaluation period.
  - The model's advertised capability—"festival-aware demand forecasting"—was **never validated on festival peaks in the holdout**.
  - Empirical verification shows that during festival weeks, MAE jumps from **3.53 to 5.13 (+45.3% error)**.
- **Temporal Leakage in Feature Calculation:**
  - `build_features.py` calculates `roll_mean_7` with `s.shift(1).rolling(7).mean()` on the entire dataset *prior* to splitting.
  - In the 90-day test set, day $t$ uses ground truth actual sales from day $t-1$ through $t-7$.
  - In supply chain operations, orders must be placed 3 to 14 days in advance. An evaluation that assumes day $t-1$ sales are already known is measuring single-step teacher forcing, not replenishment forecasting.
- **Censored Demand Neglect:**
  - In `pos_synthetic.csv`, 7,446 sales observations (3.19%) are capped by `stock_on_hand` (`stockout_flag = 1`). In high-demand categories like sweets, stockout frequency exceeds 10%.
  - `train_model.py` trains on `TARGET = "units_sold"`. On stockout days, average units sold was 60.3, but the model learned to predict 57.2.
  - The model systematically learns to under-forecast during demand surges because it treats stockout-truncated sales as true consumer demand.

#### 8. Festival Proximity Discontinuity in Feature Engineering

### [MEDIUM] Severity 3: Logic Flaws, Evaluation Inconsistencies & Dashboard Hazards

#### 9. Flawed Risk Detection & Single-Day Evaluation
- **Location:** `src/train_model.py` (Lines 114–128)
- **Code:**
  ```python
  latest_date = test_scored["date"].max()
  latest = test_scored[test_scored["date"] == latest_date].copy()
  latest["days_of_cover"] = latest["stock_on_hand"] / latest["predicted_units"].clip(lower=0.1)
  ```
- **Description:** 
  1. Risk reports are generated for **only a single day** (2026-08-25) out of the 90-day holdout.
  2. `predicted_units` is 1-day predicted demand. Dividing current stock by 1-day demand assumes daily demand is static over the planning window.
  3. Opening stock vs. closing stock inconsistency: `generate_synthetic_data.py` defines `stock_on_hand` as stock before sales, but README states it is closing stock after sales.
  4. Fixed thresholds (<2 days = stockout, >3 days = overstock) ignore replenishment lead times, review periods, and minimum order quantities.

#### 10. Distorted Evaluation Metrics in `train_model.py`
- **Location:** `src/train_model.py` (Lines 51–53)
- **Code:**
  ```python
  def mape(y_true, y_pred):
      mask = y_true > 0
      return np.mean(np.abs((y_true[mask] - y_pred[mask]) / y_true[mask])) * 100
  ```
- **Description:**
  1. Dropping `y_true == 0` discards days with zero sales, hiding intermittent demand errors.
  2. Standard MAPE is heavily skewed towards penalizing over-forecasting over under-forecasting.
  3. Supply chain industry standard is **WAPE (Weighted Absolute Percentage Error)**: $\frac{\sum |y - \hat{y}|}{\sum y}$.

### Phase 2: Forecasting Engine & Algorithmic Improvements

5. **Complete the Festival Calendar (2021–2027):**
   - Add festival dates for 2021 and 2022 into `src/festival_calendar.py` so the full historical training window has valid festival features.
   - Replace signed distance to nearest festival with **directional countdown features**:
     - `days_until_next_festival` (strictly non-negative countdown: 14, 13, ..., 1, 0)
     - `days_since_last_festival` (post-festival decay: 0, 1, 2, ...)
     - `next_festival_weight` and `next_festival_code`
6. **Correct Demand Censoring (Unconstrain Demand):**
   - When `stockout_flag == 1`, observed `units_sold` is not true demand.
   - Apply standard supply chain demand unconstraining:
     $$\hat{D}_t = \max(y_t, \text{roll\_mean\_7}_t \times \text{fest\_uplift}_t)$$
   - Train the model on unconstrained demand $D_t$ rather than censored sales $y_t$.
7. **Eliminate Multi-Step Leakage in Lag/Rolling Features:**
   - For a production replenishment horizon of $L$ days (e.g. $L=7$ days lead time):
     - Lag features must start at $\ge L$: `lag_7`, `lag_14`, `lag_21`.
     - Rolling means must be lagged by $L$:
       ```python
       df["roll_mean_7_lag7"] = g.transform(lambda s: s.shift(7).rolling(7, min_periods=1).mean())
       ```
   - This ensures the model is evaluated on inputs that would actually be available at decision time.
8. **Remove Redundant Collinear Features:**
   - Drop `store_id_code` from `FEATURE_COLS` since it is identical to `city_code`.
9. **Persist Categorical Encoders:**
   - Replace `.cat.codes` with `sklearn.preprocessing.OrdinalEncoder` or save an explicit JSON mapping:
     `outputs/categorical_mappings.json`.
   - Store category mappings alongside model weights so inference pipelines can map raw string inputs accurately.

### Phase 3: Systematic Model Training & Fine-Tuning

10. **Implement Time-Series Cross-Validation:**
    - Replace the single 90-day split with a 4-fold **Rolling Window / Expanding Window TimeSeriesSplit**:
      - Fold 1: Train 2021–2023, Validate Q1 2024
      - Fold 2: Train 2021–Q1 2024, Validate Q2 2024
      - Fold 3: Train 2021–Q2 2024, Validate Q3 2024 (evaluates festivals!)
      - Fold 4: Train 2021–Q3 2024, Validate Q4 2024 (evaluates Diwali peak!)
    - This ensures hyperparameter tuning optimizes across both festival and non-festival seasons.
11. **Align Training Objective with Supply Chain KPIs:**
    - Experiment with `objective="regression_l1"` (MAE) and `objective="tweedie"` (`tweedie_variance_power=1.1 to 1.5`) which naturally models zero-inflated, over-dispersed count data.
    - Evaluate using **WAPE** and **MASE (Mean Absolute Scaled Error)** alongside MAE and RMSE:
      $$\text{WAPE} = \frac{\sum |y_i - \hat{y}_i|}{\sum y_i}$$
12. **Automate Hyperparameter Optimization (Optuna):**
    - Implement an Optuna tuning pipeline over the following search space:
      - `learning_rate`: [0.01, 0.1] (log scale)
      - `num_leaves`: [15, 63]
      - `max_depth`: [4, 8]
      - `min_child_samples`: [20, 200]
      - `subsample` & `colsample_bytree`: [0.6, 0.95]
      - `reg_alpha` & `reg_lambda`: [1e-3, 10.0] (log scale)
    - Add early stopping with a 50-round patience window.
13. **Segment-Specific Tuning:**
    - Fine-tune Perishable and Non-Perishable models independently. Allow Perishables shorter rolling windows and higher festival weights, while Non-Perishables utilize longer seasonal trends.
14. **Connect ML Forecasting to the Regional Catalog:**
    - Replace the random generator in `build_bigbasket_regional_risk.py` with an inference script that feeds BigBasket SKU metadata and regional calendar dates through the trained LightGBM models.
